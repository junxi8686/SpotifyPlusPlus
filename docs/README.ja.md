# Spotify++

**Spotify の中のアニメーション同期歌詞 —— Xposed / LSPosed モジュール（簡体字中国語版フォーク）**

Spotify 標準の歌詞画面を、より使いやすいものに置き換えます：複数ソースの同時検索、逐字歌詞、翻訳、ローマ字、全画面表示、デスクトップ歌詞、Android Auto 歌詞。

非公式プロジェクトであり、Spotify およびいかなる歌詞プロバイダーとも無関係です。

## これは何か

Spotify++ は Spotify のプロセス内で動作する歌詞モジュールで、Spicy EX（作者 amarinne）を基に改変したもので、主に中国語圏の利用者を対象としています。Spotify の歌詞画面を引き継ぎ、複数の歌詞ソースへ同時に問い合わせ、一つの採点規則で最も適した文書を選び出して描画します —— 逐字または逐語の時間軸、翻訳、ローマ字、そして全画面・デスクトップ・Android Auto などの表示方法です。

どの歌詞を表示するかがこのモジュールの要点です。Spotify 標準の歌詞は一つだけで、中国語では繁体字・行単位の時間軸であることがよくあります。同じ曲でも別のソースには簡体字・逐字・翻訳付きの版が存在することがあります。モジュールはどのソースが最良かをあらかじめ決めず、各候補を一つずつ測ってから合計点を比べます。

**このリポジトリは改変版であり、元のプロジェクトではありません。** 上流の著作権は原作者に帰属し、このリポジトリの変更部分も同じ **AGPL-3.0** で公開されています —— 詳しくは [LICENSE](../LICENSE)、[NOTICE](../NOTICE)、[MODIFICATIONS.md](MODIFICATIONS.md) を参照してください。

## 1.5 の新機能と修正

### 新機能

- **レイアウトをその場で調整できる** —— エディタで変更すると即座に反映され、閉じて開き直す必要はありません。各要素は個別に表示・非表示にできます
- **歌詞の表示文字**（任意、既定は「変換しない」）—— 中国語の歌詞を表示時に簡体字へ統一できます。語句単位で判定するため「頭髮」と「出發」もそれぞれ正しく変換されます。**既定はオフで、設定しない限り何も変わりません**
- **歌詞の並び順アルゴリズムを刷新** —— 逐字優先、簡体字優先、翻訳は多いほど良く、長さは合うほど良く、言語は曲と一致すること。これらを総合的に採点し、最も適した文書を選びます。規則は[次の節](#歌詞はどう選ばれるか)を参照
- **自動選択はすべてのソースに問い合わせる** —— 一つ返ってきただけで止まりません。後からソースが返れば再比較し、点が高いほうを使います
- **任意で使える機械翻訳の連携先を追加** —— 設定で自分の AppID とキーを入力すると有効になります。既定は引き続きアカウント不要のオンライン翻訳です
- **バックアップの復元時に、どの鍵を入力し直す必要があるかを知らせる** —— 認証情報は端末内で暗号化して保存されるため、機種変更や再インストールの後では復号できません。復元時に項目ごとに知らせます

### 修正した問題

- Spotify 9.1.90 以降、フローティングウィンドウの歌詞が表示された直後に消えていた
- Spotify がホストウィンドウを閉じると、フローティングウィンドウも一緒に閉じられていた
- AI 翻訳が中断されると、保存済みの結果が完全なものと見なされ、歌詞の行が欠けていた
- AI 翻訳の再試行で、すでに支払い済みの結果を捨てて二重に課金していた
- 歌詞のグラデーションと字間がなめらかでなかった
- 歌詞の位置に歌詞ではなく Spotify 内部の画面名が表示されていた。すでにキャッシュに入ったそうした内容も読み出されていた
- 中国語曲の歌詞翻訳が丸ごと捨てられ、一行も翻訳されなかった
- 歌詞が「翻訳中」のまま止まり、画面が何も操作できなかった
- 翻訳に失敗しても何も表示されなかった
- 繰り返し現れる行（サビなど何度も歌われる箇所）に翻訳が付かなかった
- キーが必要なソースがまったく選ばれず、歌詞も見つからなかった
- ソース一覧で、歌詞を取得できないソースが使えるように見え、タップしても反応しなかった
- バックアップの復元が、端末でまだ使えている鍵を上書きしていた
- ソースをまたぐ歌詞の混合を廃止。一方の時間軸ともう一方のテキストを組み合わせる機能で、行数が合わないと見た目は正常でも歌い進むうちにずれていた
- 日本語と韓国語のインターフェースで不足していた文言を補完。以前はそこに英語が表示されていた
- 歌詞の下に「歌詞ソース」の行が表示されなくなった

## 歌詞はどう選ばれるか

1 回の選択の入力は、**有効なソース**がこの曲に対して返したすべての候補です。各候補は自分の情報を持っています：時間軸のレベル、歌詞テキスト、翻訳の網羅率、文書の長さ、マッチ方式など。規則は二段階です。まず「そもそもこの曲ではない」文書を除外し、残った文書を採点して、合計点が最も高いものが選ばれます。

### 手順1 別バージョンを除外する

ある文書の行が、録音の終わりを過ぎて **10 秒以上** まで並んでいる場合、それはこの版の録音の歌詞ではありません。その回から直ちに除外します。

この判定は一方向です：**早く終わるのは問題になりません。** アウトロ、フェードアウト、器楽の締めくくりはどれも歌詞を録音より短くしますが、これは正常なことで、減点も除外もしません。

### 手順2 七項目の採点

満点は 20 点で、七項目の合計です。各項目は候補そのものから読み取ります。ただし長さの項目だけはその回のすべての候補を見ます（後述）。

| 項目 | 満点 | 何を見るか | なぜ見るか |
|---|---|---|---|
| 時間軸の精度 | +4 | 行内の進行（逐字・逐語）は満点；行単位は +2；時間軸なしは 0 | ハイライトは歌唱に貼り付いている必要があります。行内の時間点があれば一文字ずつ進み、行単位では行ごとに飛ぶだけです。中国語の歌詞のソースは通常、一文字に一つの時間点を与えます |
| 簡体字の度合い | +5 | まず文書が中国語かどうかを判定し、「簡体字専用字 ÷（簡体字専用字 + 繁体字専用字）」で段階化：95% 以上は満点、次に 80%、60%、40%、20% と一段ずつ下がります | 同じ曲の簡体字版と繁体字版は別々の文書であり、読者が読むのは文字です。異体字の差がまったくない文書（例えば「我今天很好」）は満点とします —— そもそも繁体字が含まれていないからです |
| 翻訳の網羅率 | +2 | ソース自身の翻訳が付いた行 ÷ 翻訳できる行（間奏・空行は分母に入れない）に 2 を掛けた値 | 翻訳は一行ずつ読むもので、訳されているほど理解できる部分が増えます。割合で与えるため、26% と 74% は並ばず、一行訳すごとに少しずつ増えます |
| 長さの適合 | +3 | 文書の時間軸の終点が録音の終わりに最も近いもの +3、次が +2、+1、それ以降は 0 | 歌詞文書と録音は同じ版ではないことがよくあります（ライブ版、編集版、延長版）。聴くほどずれていく原因はここにあり、時間軸の精度ではありません |
| 完全性 | +1 | 曲全体を覆っていれば +1、断片だけなら 0 | サビだけの断片は、時間軸がどれだけ正確でも唯一のソースには向きません |
| マッチの身元 | +2 | Spotify ID の完全一致 +2；ソース自身の曲 ID マッピング +1；検索命中 0 | 完全な ID は「この候補はこの曲について問い合わせた」ことを示します。検索命中は名前が似ていることしか示しません。Spotify 標準のソースはこの 2 点を受け取りません —— そもそもこの ID で引いているからです |
| 言語の一致 | +3 | 候補テキストの言語が曲自体の言語と一致すれば +3；不一致または判定不能は 0 | 中国語曲に中国語字幕を付けるのと、英語曲に中国語字幕を付けるのは別のことです。曲の言語は同じ回の Spotify 標準文書から読み取るので、追加の要求も待ち時間も要りません |

**中国語かどうかの判定はヒューリスティックで、個々の文字ではなく比率で見ます：** 仮名がサンプルテキストの 10% を超えれば日本語と判定します（中国語曲に日本語の一節が混じっても中国語曲なので、比率で見ます）。漢字が 10 文字未満では判定できません。漢字密度が 25% 未満なら中国語テキストではないと判定します（英語曲に中国語の単語が少し混じっても中国語歌詞にはなりません）。判定に通らない場合はこの項目が 0 点になるだけで、減点も除外もありません —— つまり判定を誤っても文書が点を失うだけで、誤った文書が上に来ることはありません。

**長さはその回の順位で採点し、固定の秒数は使いません。** ある回を実測したところ、すべてのソースの時間軸が録音より 24 秒から 39 秒短い状態でした。「2 秒以内の差なら 3 点」といった固定の段階だと、その回はどの候補も 0 点になり、どれがより近いのかまったく分かりません。順位で採点すれば、その回は 3、2、1、0、0 と読めます —— その回にある唯一の証拠で候補を分けられます。代償は、ある文書の点数が同じ回に誰がいるかに依存し、候補が入れ替われば変わりうることです。

**翻訳は有無ではなく行の割合で採点します。** 全体が翻訳されていれば満点の 2 点、半分なら約 1 点、なければ 0 点です。

**マッチの身元は加点であって、関門ではありません。** 完全一致は自動的に勝つわけではありません。それは正しい曲に問い合わせたことだけを示し、歌詞に時間軸があるか、完全か、簡体字かは示しません —— それらは他の項目が判断します。逆に、検索で見つかった文書も「検索で出てきたから」という理由で除外されることはありません。

### 同点、手動指定、安定性

- **合計が同じとき**は設定の「ソース順序」で決まります。それも同じなら組み込みの固定順、最後に候補 ID で決まります。候補 ID の層があるため、同じ回の結果はコールバックの到着順に依存しません。
- **すでに選ばれている文書は、同点または内容が同じであればその座を保ちます。** コールバックの順序が変わったり再起動したりしても入れ替わり続けることはありません。挑戦者は厳密に高い点でなければ交代できません。
- **手動指定**：ある候補を手動で選んだら、その曲ではそれを固定で使います。その候補が一時的に取得できない場合、画面は自動の結果を一時的な代替として明示したうえで表示し、指定を消すことはありません。
- **二つの選択モード**：既定の「自動」はソース間で合計点をまとめて比べます。「ソース順」はあなたが並べた順に従い、歌詞がある最初のソースが勝ち、そのソースの中でだけ合計点を比べます。曲ごとの手動指定はどちらのモードでも有効です。

### この規則が意図的に見ないもの

マッチ信頼度、背景ボーカル・デュエット・クレジット情報といった「ソース能力」の数、時間軸の健全性、そしてソースの身元 —— これらは採点に加わりません。依然としてソース一覧に表示され、判断の材料になりますが、今回どれを使うかは決めません。ソースは同点のときだけ順序として登場します。

## 段階比較と重み付きスコア

1.4 の規則はゼロから作ったものではありません。v1.1 は**段階ごとの比較**を使い、1.4 はそれを**重み付きの合計**に置き換えました。どちらも適切な歌詞を選べますが、違いはトレードオフにあります。

### v1.1 段階ごとの比較

決まった順序で段階を追って問い、**最初に差が出た段階で勝敗が決まります**：

```
越界の除外 → 時間軸のレベル → 完全性 → ソース自身の翻訳/転写 → 簡体字の度合い
        → マッチ方式 → 能力の数 → 時間軸の健全性 → マッチ信頼度 → 長さの距離
        → ソースの固定順 → 候補 ID
```

各段階は「等級、真偽値、またはしきい値」で、重みはありません。利点は**単純で予測しやすい**ことです。決定経路が一本しかなく、同じ二つの文書はどの回でも相対順序が同じで（他の候補とは無関係）、ログは一本の連鎖として読めます。「逐字は必ず行単位に勝つ」といった硬い規則も表現しやすい。代償は**優先順位は表せても、差の大きさは表せない**ことです。二つの信号が互いを補えず、しかも後ろの段階ほど手前のどの段階の差でも丸ごと飛ばされます —— 例えば信頼度や長さの距離はかなり後ろにあり、手前の段階で差が出た時点で判断にまったく関与しません。旧規則はさらに音節レベルを語レベルより上に置いていました（ラテン文字では一音節に一つの時間点と語レベルは確かに違います）。1.4 は両者に同じ点を与え、同点規則で決めます。

### 1.4 重み付き合計

```
別バージョンの除外 → 七項目の合計 → 同点ならソース順 → 候補 ID
```

七項目にはそれぞれ配点があり、ある面の強みが別の面の不足を補えます。等級も段階に置き換わりました。計算できる例を挙げます：**逐字 + 簡体字**の文書と、**行単位 + 繁体字だが完全 ID で命中した**文書 —— 時間軸の項目は 4 対 2、簡体字の項目はさらに最大 5 点差を開き、完全 ID は 2 点の価値しかないので、逐字・簡体字のほうが前に出られます。逆に、両者の時間軸が同レベルで簡体字の度合いも近ければ、完全 ID の 2 点やソース順の前後で帰属が決まります。

代償もはっきり書いておきます。合計点のうち一つはその回の順位なので、点数は**候補集合の関数**であり、候補が入れ替われば同じ文書でも合計点が変わりえます。回をまたいで比べるときは、合計点だけでなくログの項目別の値を見てください。

### それぞれ何が得意か

- **旧規則は予測しやすさが得意です。** 段階が少なく、順序が明確で、各手順を暗記できます。同じ二つの候補の相対順序は他の候補に依存しません。「逐字は常に行単位より優先」といった硬い結論を最も直接に表現できます。
- **新規則は同時に天秤にかけるのが得意です。** 時間軸、簡繁、翻訳、長さ、完全性、マッチの身元、言語の七項目をまとめて計算し、度合いの差が段階になり、弱い項目を強い項目で補えます。長さの項目をその回の順位で採点するため、「どのソースも数十秒ずれている」ような回でも優劣を分けられます。

両者は置き換えの関係にあります。v1.1 が前者、1.4 が後者で、同時に併存しているわけではありません。違いは何を前に置くかだけです：**確定的な順序か、重み付けできるトレードオフか。**

## 機能

### 歌詞の取得

- **複数ソースの同時検索** —— 有効なソースすべてに同時に問い合わせ、最も速く使えるものが先に表示され、厳密に点が高い候補だけがそれを置き換えます
- **逐字歌詞**（カラオケ効果）。逐字・逐語・行単位・時間軸なしの四段階に対応
- **スマートマッチング** —— Spotify ID の完全一致、曲名検索、簡体字↔繁体字の相互検索、別名と表記ゆれ（例：`反乌托邦 - 拼接版` と `拼接乌托邦`）に対応
- **曲名で手動検索** —— 自動マッチに失敗したときは自分で曲名を検索し、返ってきた結果から選び、ID で直接取得できます
- **ソース一覧** —— ソースごとに個別に確認でき、マッチ状態・時間軸レベル・翻訳・能力を表示します。歌詞を取得できないソースははっきり示され、手動で先頭に固定できます
- **ローカルキャッシュ** —— 一度取得した歌詞は保存され、同じ曲をもう一度再生しても再要求は不要です

### 歌詞の表示

- **翻訳**と**ローマ字／読み**
- **全画面の歌詞画面**（Spotify 標準の歌詞ページを引き継ぎます）
- **デスクトップ歌詞**と **PiP（ピクチャインピクチャ）** 歌詞
- **Android Auto 歌詞** —— 全画面プレイヤーとカード
- **HyperGlow** への歌詞配信
- デュエット表示、背景ボーカルの印、共有カード

### マッチ品質

- **採点による選別** —— 七項目の重み付き。簡繁は割合で段階化し、翻訳は網羅率で採点します
- **越界文書の除外** —— 録音より 10 秒以上長い文書は別バージョンとして除外します
- **汚染文書のフィルタ** —— 内容が疑わしい応答は受け取りません
- 時間軸の健全性、マッチ信頼度などの項目は、手動で判断できるよう引き続きソース一覧に表示されます

### その他

- **簡体字中国語の完全なインターフェース**、ほかに English / 日本語 / 한국어 / Русский
- **バックアップと復元** —— 設定、ソース順序、曲ごとの指定、カタログ全体、キャッシュ、フォントを一度に持ち出せます

## 歌詞ソースと認証情報

モジュールは複数の歌詞ソースに同時に問い合わせます。Spotify 標準の歌詞に加えて、いくつかの第三者の歌詞ライブラリとプラットフォームです。同じソースでも曲によって挙動は大きく異なります。時間軸がより細かいもの、よく翻訳が付くもの、繁体字しかないもの —— まさにそれがこの採点規則の扱う問題です。どれがどれかを知る必要はありません：**自動モードでは、有効なソースすべてが合計点で一緒に競います**。

### キーが必要なソースが一つある

一つだけ、自分のクライアントキーが必要なソースがあります：

1. 設定に示される案内に従って、そのサービスで申請します
2. **設定 → Spotify++ → クライアントキー** に入力します
3. 形式が合わない場合は保存を拒否し、その旨を表示します

キーがない場合、またはキーが無効な場合、そのソースは自動的に飛ばされ、残りのソースは通常どおり動作します。キーはこの端末にのみ暗号化して保存され、**バックアップとともに別の端末へ移ることはありません**（[バックアップと移行](#バックアップと移行)を参照）。

### 自分で制御できる部分

- **どのソースを有効にするか** —— 不要なものは切れます。切ったソースは選択の回でそもそも問い合わせません
- **ソース順序** —— 自動モードの同点裁定であり、「ソース順」モードの優先順位でもあります
- **選択モード** —— 自動（合計点をまとめて比較）またはソース順（歌詞がある最初のソースが勝つ）
- **曲ごとの指定** —— ソース一覧で特定の候補を手動で固定できます

## インストール

### 前提条件

| 項目 | 要件 |
|---|---|
| システム | Android 8.1 以上（minSdk 27、targetSdk 35） |
| モジュールフレームワーク | **Xposed / LSPosed**（推奨、root が必要）または **LSPatch**（root 不要、Spotify へのパッチ適用は自分で行う）。モジュールは Xposed API 102 を使用 |
| Spotify | 本ビルドは **9.1.88 – 9.1.90** に合わせて調整；それより古い版、ベータ版、第三者の改変版では動作しないことがあります |
| モジュールのバージョン | 1.5（versionCode 8） |

> モジュールは Xposed フレームワークの注入に依存しており、**未パッチの Spotify では動作しません**。

### 手順

1. [Releases](https://github.com/junxi8686/SpotifyPlusPlus/releases) から最新の APK をダウンロードしてインストール
2. **LSPosed** → **モジュール** → **Spotify++** を有効化
3. **スコープ**で `Spotify` にチェック
   - Android Auto の歌詞も必要な場合は `Android Auto` にもチェック
4. **Spotify を強制停止**（設定 → アプリ → Spotify → 強制停止）
5. Spotify を開き直す

> ⚠️ **手順 4 は省略できません。** APK をインストールしても Spotify のプロセスは**再起動されず**、LSPosed はプロセス起動時にのみモジュールを読み込みます。この手順を飛ばすと古いコードを試すことになります —— トラブルシューティングで最も混乱を招く原因です。
>
> **更新の場合も同じです**：新しい APK を上書きインストールし、同じように強制停止して Spotify を開き直してください。LSPatch を使う場合は「バージョンコードの上書き」を有効にしてください。

## 初回起動

インストール後は、曲を再生するだけで歌詞が自動的に表示されます。最初の一曲で良い結果を得るため、モジュールは有効なソースすべてに同時に問い合わせ、後からソースが返ってくれば再比較します。

### 設定の場所

入口は二つです：

- **設定** —— Spotify の設定内にある **Spotify++** セクション。すべてのスイッチはここにあります：歌詞ソース（有効化、順序、選択モード、クライアントキー）、翻訳（バックエンド、対象言語、キャッシュ）、AI 翻訳と読み、インターフェースと描画、キャッシュの消去、エクスポートとインポート
- **ソース一覧** —— 歌詞画面の右下にあるソースボタン。この曲で各ソースがどうマッチしたかを見たり、個別に再確認したり、手動で指定したりできます

### 調整のヒント

| 望む結果 | やり方 |
|---|---|
| 逐字歌詞を優先したい | 既定で有効、設定は不要 |
| 特定のソースを優先したい | 設定 → ソース順序でそれを先頭へ移動；またはソース一覧でこの曲に手動指定 |
| 中国語曲を簡体字で表示したい | 既定で有効（簡体字の度合いが採点に加わります） |
| 歌詞に追従させない／手動でスクロールしたい | 「再生に追従」をオフ |
| 歌詞がずれる | 設定 → 歌詞同期をリセット |
| 問い合わせるソースを一つ減らしたい | 設定 → そのソースをオフ |

## バックアップと移行

**設定 → 設定とデータを書き出す** で JSON を一つ書き出します（既定では `Downloads/Spotify++/SpotifyPlusPlus-backup.json`、保存先は自分で選ぶこともできます）。復元は **設定とデータを読み込む** で行います。

### バックアップに含まれるもの

| 内容 | 説明 |
|---|---|
| すべての設定 | インターフェース、描画、動作、選択モード |
| ソース順序と曲ごとの指定 | あなたが調整した優先順位と曲単位の選択 |
| カタログ全体 | 各曲にどのソースの候補があるか、どうマッチしたか、確認済みかどうか |
| 歌詞と翻訳のキャッシュ | データベースを丸ごと複製するため、復元後に歌詞を再ダウンロードする必要も翻訳を再要求する必要もありません |
| インポートしたフォント | カスタムフォントファイルも一緒に移動し、復元時はこの端末の新しいパスを指します |
| 認証情報の暗号文 | クライアントキー、AI サービスのキー、翻訳 API の AppID とキー。このバックアップを書き出したインストールでしか復号できず、機種変更後は入力し直しが必要です（下記参照） |
| 少量の実行時状態 | キーのリビジョンとアクセス状態。復元後に古い結果が混ざるのを防ぎます |

### 意図的に含まれないもの

- **診断ドラフトとキャプチャバッファ** —— 進行中のレポートの一時状態であり、移行する対象ではありません
- **言語モデルパック** —— 数十 MB あり、いつでも再ダウンロードできます。設定側が新しい場所を指し直します
- **平文の認証情報** —— 暗号文のみです。以下を参照

### 認証情報は持ち出せない

認証情報はこの端末で暗号化して保存され、暗号化に使う鍵はシステムの Keystore にあり、この端末上での Spotify の身元に紐づいていて、**バックアップファイルには書き込まれません**。したがって：

- 同じ端末であれば、モジュールの更新、Spotify の更新、モジュールのアンインストールと再インストールをしても、認証情報はそのまま使えます
- 機種変更、Android ユーザーの変更、または Spotify のデータを消去した後は、バックアップ内の暗号文を復号できません —— **新しい端末で入力し直す必要があります**
- モジュールが**鍵をインポートしたり移行したりすることはありません**。どのメッセージでもそのようには案内しません

復元の際、この端末にすでに使える認証情報がある場合、**ファイル内にあってもここで読めない値で上書きされることはありません**。復元が完了すると、どの認証情報を設定で入力し直す必要があるかを項目ごとに知らせます。

### 復元のルール

- **ファイルにある項目は同名の項目を上書きし、ファイルにない項目はそのまま残ります**（古いバージョンのバックアップも読み込め、覆われなかった部分が消えることはありません）
- 現在のバージョンより新しいバックアップは、推測せずに拒否します
- 復元後、カタログと翻訳キャッシュは **Spotify を再起動するまで反映されません**

関連文書：[MODIFICATIONS.md](MODIFICATIONS.md)（AGPL の変更声明）、[FEATURES_USER.md](FEATURES_USER.md)（機能一覧）、[READINGS.md](READINGS.md)（読みと転写のガイド）。

### 環境

|---|---|

| Gradle | 8.14.2（wrapper 同梱） |

### コマンド

```bash
git clone https://github.com/junxi8686/SpotifyPlusPlus.git
cd SpotifyPlusPlus
./gradlew :app:assembleDebug          # 出力は app/build/outputs/apk/debug/

Windows では `gradlew.bat` を使います。

### ユニットテストのグループ

テストはグループ単位で実行でき、毎回すべてを走らせる必要はありません：

./gradlew :app:testDebugUnitTest -PtestGroup=lyrics        # 歌詞関連

./gradlew :app:testDebugUnitTest -PtestGroup=corpus        # 言語のゴールデンサンプル
```

利用できるグループ：`settings`、`diagnostics`、`hooks`、`lyrics`、`lyrics-ai`、`lyrics-session`、`corpus`。ほかに明示的に有効化する必要がある評価ツール（`-PtestTools=jp-export`、`-PtestTools=model-survey`）があり、これらはファイルを書き出したり有料サービスを呼び出したりするため、回帰テストには含まれません。

## トラブルシューティング

<details>
<summary><b>インストールしたが反応がない／機能が効かない</b></summary>

1. LSPosed でモジュールが有効になっていること、**スコープで Spotify にチェックが入っている**ことを確認する
2. **Spotify を強制停止してから開き直す** —— 必須です
3. Spotify のバージョンが対応範囲か確認する（本ビルドは 9.1.88 – 9.1.90 に対応）

</details>

<details>
<summary><b>歌詞が繁体字だが簡体字がほしい</b></summary>

簡体字の度合いは採点に加わるため、通常は簡体字の文書が自動的に勝ちます。それでも繁体字なら：

1. **ソース一覧**を開き、簡体字の歌詞を提供するソースがあるか見る
2. あればそれを手動で指定する
3. なければ、その曲にはまだ簡体字の歌詞が存在しません —— 採点規則が勝手に作ることはできません

</details>

<details>
<summary><b>あるソースがいつも見つけられない</b></summary>

**ソース一覧**でその行をタップして個別に確認します：

- **チェック** → そのソースにこの曲の歌詞がある
- **赤いバツ** → そのソースに本当に無いか、ネットワークが通じていない

歌詞を取得できないソースは、使えるように見えて反応しないのではなく、明確に利用不可として表示されます。**収録状況は動的に変わる**ことに注意してください —— 今日無いからといって今後も無いとは限りません。

</details>

<details>
<summary><b>キーが必要なソースが何も返さない</b></summary>

1. 設定でキーが正常に保存されたことを確認する（保存時には必ず何か表示されます）
2. ソース一覧で**一度手動でタップ**する —— 手動確認は「明示的な回復」の経路を通り、以前のアクセス制限を解除できます
3. サーバーに拒否されたキーはそのソースを一時停止させます

</details>

<details>
<summary><b>機種変更・初期化の後で復元するには</b></summary>

**エクスポートとインポート**を使います。注意点：

- 設定、ソース順序、カタログ、キャッシュは復元できます
- 認証情報の暗号文はファイルと一緒に移動しますが、復号する鍵は端末に紐づいています —— **新しい端末で入力し直す必要があります**
- 復元が完了すると、どの項目を入力し直す必要があるかをモジュールが知らせます

</details>

<details>
<summary><b>歌詞が同期しない／だんだんずれる</b></summary>

まずソース一覧を見ます。時間軸の終点と録音の終わりが大きく離れていれば、その文書は録音と同じ版ではないので、手動で別のものに替えられます。

時間軸自体に問題がなければ：

設定 → **歌詞同期をリセット**。保存されたオフセットを消し、モジュールを再生クロックに合わせ直します。

</details>

## 既知の問題と制限

- **点数はその回の候補に依存します** —— 長さの適合は順位で採点するため、候補が入れ替われば同じ文書の合計点も変わりえます
- **言語の判定はヒューリスティックです** —— 仮名がほとんど無い日本語曲は中国語と判定されることがあります。英語が多い中国語曲は漢字密度のしきい値を下回ることがあります。韓国語の中の漢字は別扱いされません。判定を誤るとこの項目の点が減るだけで、加点されることはありません
- **一部の曲は遅いソースでマッチに時間がかかります** —— ネットワークの要因で、モジュールの問題ではありません
- **Android Auto の歌詞**は一部の車載機で十分に検証されていません
- **ごく一部の曲**では歌詞と録音の長さが一致しません。10 秒以上の越界は除外されますが、10 秒以内でもずれが残ることがあります
- **読みは規則と辞書に基づきます** —— 普通話の多音字、日本語の芸術的な読み、キリル文字の転写、ギリシャ語の静的テーブルにはいずれも既知の限界があります
- **root なしの LSPatch の方法**は「ダウングレード・ログイン・アップグレード」の手順に依存しており、ログインや整合性チェックが失敗することがあります
- **HyperGlow への配信**には、その機能に対応した端末が必要です

問題が起きたら [Issues](https://github.com/junxi8686/SpotifyPlusPlus/issues) で報告してください。以下の情報を添えてください：

- Spotify のバージョン
- モジュールのバージョン
- 再現手順
- 関連するスクリーンショット

## 上流からの変更点

本リポジトリは本プロジェクトの **v1.1** の上に上流 Spicy EX の変更を続けて取り込んでいます。1.4 で並び順の規則を置き換え、1.5 では上流 **v2.0.41** を取り込み、以下の調整を行いました：

### 簡体字中国語

- `values-zh-rCN` を追加し、すべての文字列リソースを網羅
- 上流の「Java が参照しているがリソースに存在しない」ために中国語インターフェースが英語に戻る問題を修正
- 歌詞のクレジット、エラー表示などの動的な文言を中国語化
- 一部の端末で言語一覧が現在の言語しか表示されず、切り替えても戻れない問題を修正

### 歌詞マッチング

- **重み付き採点による選別**（1.4）—— 上流 v2.0.0 は「ソース優先」（主ソースを決め、そのソース内でだけ時間軸を比べる）に変えたため、より良い代替ソースが主ソースを置き換えられなくなりました。本リポジトリの v1.1 は品質優先の段階比較に戻し、1.4 ではさらに七項目の重み付き合計に置き換えました。[段階比較と重み付きスコア](#段階比較と重み付きスコア)を参照
- **複数ソースへの同時リクエスト** —— 上流はソースを一つずつ順に要求するため、待ち時間が全ソースの合計でした。現在は同時に発行し、最も速く使えるものを先に表示し、点が高いときだけ置き換えます
- **曲名で歌詞を検索** —— 自動マッチに失敗したときは手動で検索し、自分で選べます
- 簡体字↔繁体字の相互検索と別名・表記ゆれ（「一文字違うだけで別の曲として扱う」問題を修正）
- **ソース一覧は曲ごとに自動確認を一度だけ**行い、成功のたびに通知することもなくなりました
- **別バージョンの文書を除外** —— 録音より 10 秒以上長い候補は比較に参加しません

### バックアップとその他

- **バックアップの範囲を 2 つのストアから、設定・ソースの選択・カタログ・キャッシュ・フォント・認証情報の暗号文（書き出したインストールでのみ復号できる）へ拡張** —— 上流は設定とキーだけをバックアップしていたため、読み込んでもカタログが空でソースも未選択でした
- **認証情報の保持規則** —— 復元時に、この端末でまだ使えるキーは上書きせず、どれを入力し直す必要があるかを知らせます
- 使われなくなった歌詞ソースを一つ削除。古い設定や古いバックアップに残った項目も問い合わせません
- 誤った宛先を指していた GitHub リンクを 3 か所修正
- 設定の「問題を報告」の入口を削除（ドラフトは上流宛で、このリポジトリには届きません）
- Spotify 9.1.88 – 9.1.90 の曲取得とフローティングウィンドウに対応（上流の書き方では新しい版で `NoSuchMethodException` が投げられ、自動検索が丸ごと機能しなくなります）
- 翻訳の経路を修正：中国語の翻訳が捨てられる、「翻訳中」で止まる、失敗しても表示がない、繰り返し行に翻訳が付かない

詳しくは [MODIFICATIONS.md](MODIFICATIONS.md) と [FEATURES_USER.md](FEATURES_USER.md) を参照してください。
