# Spotify++

**Spotify 안의 애니메이션 동기화 가사 — Xposed / LSPosed 모듈 (중국어 간체 포크)**

Spotify 기본 가사 화면을 더 쓸 만한 것으로 바꿉니다: 여러 소스 동시 검색, 글자 단위 가사, 번역, 로마자 표기, 전체 화면 렌더링, 데스크톱 가사, Android Auto 가사.

비공식 프로젝트이며 Spotify 및 어떤 가사 서비스와도 무관합니다.

## 무엇인가

Spotify++는 Spotify 프로세스 안에서 동작하는 가사 모듈로, [Spicy EX](https://github.com/amarinne/spicy-ex)(작성자 [amarinne](https://github.com/amarinne))를 기반으로 수정한 것이며 주로 중국어 사용자를 대상으로 합니다. Spotify의 가사 화면을 대신 맡습니다: 여러 가사 소스에 동시에 질의하고, 하나의 채점 규칙으로 가장 적합한 문서를 골라 렌더링합니다 — 글자 또는 단어 단위 시간축, 번역, 로마자 표기, 그리고 전체 화면, 데스크톱, Android Auto 같은 표시 방식입니다.

어떤 가사를 고르는지가 이 모듈의 핵심입니다. Spotify 자체 가사는 한 벌뿐이고, 중국어 곡에서는 번체에 줄 단위 시간축인 경우가 많습니다. 같은 곡이라도 다른 소스에는 간체에 글자 단위이고 번역이 붙은 버전이 있을 수 있습니다. 모듈은 어느 소스가 가장 좋은지 미리 정하지 않고, 모든 후보를 하나씩 재어 총점을 비교합니다.

**이 저장소는 수정판이며 원래 프로젝트가 아닙니다.** 상류의 저작권은 원저작자에게 있고, 이 저장소의 수정 부분도 같은 **AGPL-3.0**으로 배포됩니다 — [LICENSE](../LICENSE), [NOTICE](../NOTICE), [MODIFICATIONS.md](MODIFICATIONS.md)를 참고하세요.

## 1.4 새로운 기능과 수정

### 새로운 기능

- **완전히 새로운 가사 정렬 알고리즘** — 글자 단위 우선, 간체 우선, 번역은 많을수록 좋고, 길이는 더 잘 맞을수록 좋으며, 언어는 곡과 일치해야 합니다. 이를 종합한 점수로 가장 적합한 문서를 고릅니다. 규칙은 [다음 절](#가사는-어떻게-선택되는가)을 참고하세요
- **자동 선택은 모든 소스에 물어봅니다** — 하나가 답했다고 멈추지 않습니다. 이후 소스가 반환되면 다시 비교해 점수가 높은 쪽을 씁니다
- **선택 사항인 기계 번역 인터페이스 추가** — 설정에서 자신의 AppID와 키를 입력하면 켜집니다. 기본값은 여전히 계정이 필요 없는 온라인 번역입니다
- **백업을 복원하면 어떤 키를 다시 입력해야 하는지 알려 줍니다** — 자격 증명은 이 기기에 암호화되어 저장되므로 기기를 바꾸거나 다시 설치한 뒤에는 풀 수 없고, 복원할 때 항목별로 알려 줍니다

### 수정된 문제

- 중국어 곡의 가사 번역이 통째로 버려져 한 줄도 번역되지 않던 문제
- 가사가 계속 「번역 중」에 멈춰 화면에서 아무것도 누를 수 없던 문제
- 번역이 실패해도 아무런 안내가 없던 문제
- 반복해서 나오는 가사 줄(예: 후렴에서 되풀이되는 부분)에 번역이 붙지 않던 문제
- Spotify 9.1.90 이후 떠 있는 창 가사가 나타나자마자 사라지던 문제
- 키가 필요한 그 소스가 계속 선택되지 않고 가사도 검색되지 않던 문제
- 소스 목록에서 가사를 가져오지 못하는 소스가 쓸 수 있는 것처럼 보이지만 눌러도 반응이 없던 문제
- 백업을 복원하면 이 기기에서 아직 쓸 수 있는 키를 덮어쓰던 문제
- 가사 아래에 「가사 출처」 줄이 더 이상 표시되지 않음

## 가사는 어떻게 선택되는가

한 번의 선택에 들어가는 입력은 **활성화된 소스**가 이 곡에 대해 반환한 모든 후보입니다. 각 후보는 자신의 정보를 가지고 있습니다: 시간축 수준, 가사 텍스트, 번역 적용 범위, 문서 길이, 매칭 방식 등입니다. 규칙은 두 단계입니다. 먼저 「이 곡이 아닌」 문서를 배제하고, 살아남은 문서에 점수를 매겨 총점이 가장 높은 것이 선택됩니다.

### 1단계 다른 버전 제외

문서의 줄이 녹음이 끝난 뒤로 **10초 이상** 이어지면 그 문서는 이 버전 녹음의 가사가 아니므로 이번 회차에서 바로 제외합니다.

이 판정은 한 방향입니다: **일찍 끝나는 것은 문제가 아닙니다.** 아웃트로, 페이드아웃, 연주 마무리 때문에 가사가 녹음보다 짧아지는 것은 정상이며, 감점도 제외도 없습니다.

### 2단계 일곱 항목 점수

만점은 20점이고 일곱 항목을 더합니다. 각 항목은 후보 자체에서 읽어내며, 길이 항목만 이번 회차의 모든 후보를 봅니다(아래에서 설명합니다).

| 항목 | 만점 | 무엇을 보는가 | 왜 보는가 |
|---|---|---|---|
| 시간축 정밀도 | +4 | 줄 안에서 진행(글자, 단어)하면 만점, 줄 단위 +2, 시간축 없음 0 | 강조가 노래를 따라붙어야 합니다. 줄 안 시간점이 있으면 강조가 한 글자씩 지나가고, 줄 단위는 줄 전체가 건너뜁니다. 중국어 가사 소스는 보통 한 글자에 시간점 하나를 줍니다 |
| 간체 정도 | +5 | 먼저 문서가 중국어인지 판정한 뒤 「간체 전용 글자 ÷ (간체 전용 글자 + 번체 전용 글자)」로 등급을 나눕니다. 95% 이상 만점, 그다음 80%, 60%, 40%, 20%씩 한 등급 내려갑니다 | 같은 곡의 간체판과 번체판은 서로 다른 문서이고, 읽는 사람이 읽는 것은 글자입니다. 전체에 간체/번체 차이 글자가 없는 문서(예: 「我今天很好」)는 만점으로 계산합니다 — 안에 번체자가 원래 없기 때문입니다 |
| 번역 적용 범위 | +2 | 소스 자체 번역이 붙은 줄 ÷ 번역할 수 있는 줄(간주, 빈 줄은 분모에서 제외)에 2를 곱합니다 | 번역은 한 줄씩 읽는 것이므로 많이 번역될수록 더 많이 이해됩니다. 비례로 점수를 주므로 26%와 74%가 동점이 되지 않고, 한 줄 더 번역하면 조금 더 받습니다 |
| 길이 적합도 | +3 | 문서 시간축 끝점이 녹음 끝에 가장 가까운 것 +3, 다음 +2, +1, 그 뒤 0 | 가사 문서와 녹음은 같은 버전이 아닌 경우가 많습니다(라이브, 편집, 연장). 들을수록 어긋나는 원인이 여기에 있고 시간축 정밀도에 있지 않습니다 |
| 완전성 | +1 | 곡 전체를 덮으면 +1, 일부만이면 0 | 후렴 일부만 있는 문서는 시간축이 아무리 정확해도 유일한 소스로는 적합하지 않습니다 |
| 매칭 정체성 | +2 | Spotify ID 정확히 일치 +2, 소스 자체 곡 ID 매핑 +1, 검색으로 찾음 0 | 정확한 ID는 「이 후보가 바로 이 곡을 물어본 것」이라는 뜻이고, 검색 결과는 이름이 비슷하다는 뜻일 뿐입니다. Spotify 자체 소스는 이 2점을 받지 않습니다 — 원래 이 ID로 조회하기 때문입니다 |
| 언어 일치 | +3 | 후보 텍스트의 언어가 곡 자체의 언어와 일치 +3, 불일치이거나 판정할 수 없으면 0 | 중국어 곡에 중국어 자막을 붙이는 것과 영어 곡에 중국어 자막을 붙이는 것은 다릅니다. 곡의 언어는 같은 회차의 Spotify 자체 문서에서 읽으므로 추가 요청이나 대기가 필요 없습니다 |

**중국어 판정은 휴리스틱이며, 낱글자가 아니라 비율로 합니다.** 가나가 표본 텍스트의 10%를 넘으면 일본어로 봅니다(중국어 곡에 일본어 한 줄이 섞여도 여전히 중국어 곡이므로 비율을 씁니다). 한자가 10자 미만이면 판단할 수 없습니다. 한자 밀도가 25% 아래면 중국어 텍스트가 아닌 것으로 봅니다(영어 곡에 중국어 단어 몇 개가 섞인 것은 중국어 가사가 아닙니다). 판정을 통과하지 못하면 이 항목이 0점이 될 뿐이고 감점도 제외도 없습니다 — 따라서 잘못 판정해도 어떤 문서가 점수를 덜 받을 뿐, 틀린 문서가 위로 올라가지는 않습니다.

**길이는 이번 회차 순위로 점수를 주며, 고정된 초를 쓰지 않습니다.** 실제로 한 회차를 재어 보니 모든 소스의 시간축이 녹음보다 24초에서 39초 짧았습니다. 「2초 이내면 3점」 같은 고정 등급을 쓰면 이 회차의 모든 후보가 0점이 되어 누가 더 가까운지 전혀 알 수 없습니다. 순위로 점수를 주면 이 회차는 3, 2, 1, 0, 0으로 읽혀, 이 회차가 가진 유일한 근거로 후보들을 구분합니다. 대가는 문서의 점수가 이번 회차에 누가 더 있는지에 달리고, 후보가 바뀌면 달라질 수 있다는 점입니다.

**번역은 있는지 여부가 아니라 줄 비율로 점수를 줍니다.** 전체가 번역된 문서는 2점 만점, 절반 번역은 약 1점, 없으면 0점입니다.

**매칭 정체성은 가산점일 뿐 문턱이 아닙니다.** 정확히 일치해도 자동으로 이기지 않습니다. 그것은 곡을 제대로 물어봤다는 뜻일 뿐, 가사에 시간축이 있는지, 완전한지, 간체인지는 말해 주지 않으며 그 판단은 다른 항목이 합니다. 반대로 검색으로 찾은 문서도 「검색으로 나왔다」는 이유로 제외되지 않습니다.

### 동점, 수동 지정과 안정성

- **총점이 같으면** 설정의 「소스 순서」로 정하고, 그래도 같으면 내장된 고정 순서, 마지막으로 후보 ID로 정합니다. 후보 ID 단계가 있어 같은 회차의 결과가 콜백 도착 순서와 무관해집니다.
- **이미 선택된 문서는 총점이 같거나 내용이 같으면 유지됩니다.** 콜백 순서가 바뀌거나 재시작해도 계속 뒤집히지 않습니다. 도전자는 엄격히 더 높아야 자리를 넘겨받습니다.
- **수동 지정**: 후보 하나를 수동으로 고르면 그것을 고정해서 씁니다. 그 후보를 당장 가져올 수 없으면 화면이 자동 결과를 임시 대체로 사용하고 분명히 표시하며, 지정을 지우지 않습니다.
- **두 가지 선택 모드**: 기본인 「자동」은 소스들을 함께 놓고 총점을 비교하고, 「소스 순서」는 사용자가 정한 순서대로 가사가 있는 첫 소스가 이기며 그 소스 안에서만 총점을 비교합니다. 특정 곡의 수동 지정은 두 모드에서 모두 유효합니다.

### 이 규칙이 일부러 보지 않는 것

매칭 신뢰도, 배경 보컬/듀엣/저작권 정보 같은 「소스 능력」 개수, 시간축 건강도, 그리고 소스의 정체성은 점수에 참여하지 않습니다. 이들은 여전히 소스 목록에 표시되어 판단에 쓰이지만, 이번에 어느 문서를 쓸지는 결정하지 않습니다. 소스는 총점이 같을 때 순서로만 등장합니다.

## 단계별 비교와 가중 점수

1.4의 규칙은 맨바닥에서 시작하지 않았습니다. v1.1은 **단계별 비교**를 썼고, 1.4는 이를 **가중 합산**으로 바꿨습니다. 둘 다 적합한 가사를 고르며, 차이는 무엇을 포기하느냐에 있습니다.

### v1.1 단계별 비교

고정된 순서로 단계를 하나씩 내려가며 **차이가 나오는 첫 단계에서 승부가 정해집니다**:

```
범위 초과 제외 → 시간축 수준 → 완전성 → 자체 번역/음역 → 간체 정도
        → 매칭 방식 → 능력 개수 → 시간축 건강도 → 매칭 신뢰도 → 길이 거리
        → 소스 고정 순서 → 후보 ID
```

각 단계는 「등급, 불리언 또는 임계값」이고 가중치가 없습니다. 장점은 **단순하고 예측 가능**하다는 점입니다. 결정 경로가 하나뿐이라 같은 두 문서의 상대 순서가 어느 회차에서나 같고(다른 후보와 무관), 로그가 하나의 사슬로 읽힙니다. 「글자 단위는 반드시 줄 단위를 이긴다」 같은 강한 규칙도 표현하기 쉽습니다. 대가는 **우선순위는 표현해도 얼마나 차이 나는지는 표현하지 못한다**는 점입니다. 두 신호가 서로를 보완할 수 없고, 뒤에 있는 단계일수록 앞의 어느 단계에서 차이가 하나 나오면 통째로 건너뛰어집니다 — 예를 들어 신뢰도와 길이 거리는 아주 뒤에 있어서, 앞 단계의 차이가 나타나면 판단에 전혀 참여하지 못합니다. 옛 규칙은 음절 단위를 단어 단위보다 위에 두기도 했습니다(라틴 문자에서 음절당 시간점 하나는 단어 단위와 실제로 다릅니다). 1.4는 둘에 같은 점수를 주고 동점 규칙이 결정하게 합니다.

### 1.4 가중 합산

```
다른 버전 제외 → 일곱 항목 합산 → 동점이면 소스 순서 → 후보 ID
```

일곱 항목은 각각 점수가 있어 한쪽의 우세가 다른 쪽의 부족을 메울 수 있고, 등급도 구간으로 바뀌었습니다. 계산해 볼 수 있는 예를 하나 들면, **글자 단위 + 간체** 문서와 **줄 단위 + 번체이지만 정확한 ID로 일치한** 문서를 비교할 때 시간축 항목이 4 대 2이고, 간체 항목에서 최대 5점을 더 벌 수 있으며, 정확한 ID는 2점에 불과하므로 글자 단위 간체 문서가 앞설 수 있습니다. 반대로 둘의 시간축이 같은 등급이고 간체 정도가 비슷하면 정확한 ID의 2점이나 소스 순서의 앞뒤가 귀속을 가릅니다.

대가도 분명히 밝혀 둡니다. 총점 가운데 한 항목은 이번 회차의 순위이므로 점수는 **후보 집합의 함수**이고, 후보가 바뀌면 같은 문서의 총점도 달라질 수 있습니다. 회차를 넘어 비교하려면 총점만 보지 말고 로그의 항목별 점수를 봐야 합니다.

### 각각 무엇에 강한가

- **옛 규칙은 예측 가능성에 강합니다.** 규칙이 적고 층이 분명해 모든 단계를 외울 수 있으며, 같은 두 후보의 상대 순서가 다른 후보와 무관합니다. 「글자 단위는 예외 없이 줄 단위를 누른다」 같은 강한 결론을 가장 직접적으로 표현합니다.
- **새 규칙은 동시 저울질에 강합니다.** 시간축, 간체/번체, 번역, 길이, 완전성, 매칭 정체성, 언어 일곱 항목을 함께 계산하고, 정도 차이에 구간이 있으며, 약한 항목을 강한 항목으로 메울 수 있습니다. 길이 항목을 회차 순위로 채점하기 때문에 「모든 소스가 수십 초씩 어긋난」 회차에서도 우열을 가릴 수 있습니다.

두 규칙은 대체 관계입니다. v1.1이 앞의 것을 쓰고 1.4가 뒤의 것으로 바꿨으며, 동시에 함께 쓰이지는 않습니다. 차이는 무엇을 앞에 두느냐뿐입니다: **결정적인 순서, 아니면 가중할 수 있는 트레이드오프.**

## 기능

### 가사 가져오기

- **여러 소스 동시 검색** — 활성화된 모든 소스에 동시에 요청하고, 가장 빨리 쓸 수 있는 것이 먼저 표시되며, 점수가 엄격히 더 높은 후보만 그것을 교체합니다
- **글자 단위 가사**(노래방 효과), 글자, 단어, 줄, 시간축 없음의 네 단계 지원
- **스마트 매칭** — 정확한 Spotify ID, 곡 제목 검색, 간체↔번체 상호 검색, 별칭과 표기 변형(예: 「反乌托邦 - 拼接版」과 「拼接乌托邦」)을 지원합니다
- **이름으로 직접 검색** — 자동 매칭이 실패하면 곡 제목을 직접 검색해 결과에서 고르고, ID로 바로 가져옵니다
- **소스 목록** — 소스마다 따로 확인하고 매칭 상태, 시간축 수준, 번역과 능력을 표시합니다. 가사를 가져오지 못하는 소스는 분명히 표시되고 수동으로 맨 위에 고정할 수 있습니다
- **로컬 캐시** — 한 번 가져온 가사는 저장되어 같은 곡을 다시 들을 때 다시 요청하지 않습니다

### 가사 표시

- **번역**과 **로마자 / 독음**
- **전체 화면 가사 화면**(Spotify 기본 가사 페이지를 대신함)
- **데스크톱 가사**와 **PiP(화면 속 화면)** 가사
- **Android Auto 가사** — 전체 화면 플레이어와 카드
- **HyperGlow** 가사 전송
- 듀엣 보기, 배경 보컬 표시, 공유 카드

### 매칭 품질

- **점수로 최선 선택** — 일곱 항목 가중, 간체/번체는 비율로 등급을 나누고 번역은 적용 비율로 점수를 줍니다
- **범위 초과 문서 제외** — 녹음보다 10초 이상 긴 문서는 다른 버전으로 보아 제외합니다
- **오염 문서 필터링** — 내용이 의심스러운 응답은 거부합니다
- 시간축 건강도, 매칭 신뢰도 같은 항목은 여전히 소스 목록에 표시되어 직접 판단할 수 있습니다

### 기타

- **완전한 중국어 간체 인터페이스**, 그 외 English / 日本語 / 한국어 / Русский
- **백업과 복원** — 설정, 소스 순서, 곡별 선택, 전체 카탈로그, 캐시와 글꼴을 한 번에 가져갑니다

## 가사 소스와 자격 증명

모듈은 여러 가사 소스에 동시에 질의합니다: Spotify 자체 가사에 더해 여러 서드파티 가사 라이브러리와 플랫폼입니다. 같은 소스도 곡에 따라 결과 차이가 큽니다. 어떤 것은 시간축이 더 세밀하고, 어떤 것은 번역이 자주 붙고, 어떤 것은 번체만 있습니다 — 바로 이것이 채점 규칙이 다루려는 문제입니다. 그것들이 무엇인지 알 필요는 없습니다: **자동 모드에서는 활성화된 모든 소스가 함께 총점을 겨룹니다.**

### 키가 필요한 소스 하나

소스 하나는 자신의 클라이언트 키가 필요합니다:

1. 설정에 있는 안내에 따라 해당 서비스에서 발급받습니다
2. **설정 → Spotify++ → 클라이언트 키**에 입력합니다
3. 형식이 맞지 않으면 저장을 거부하고 안내를 표시합니다

키가 없거나 키가 만료되면 그 소스는 자동으로 건너뛰고 나머지 소스는 평소대로 동작합니다. 키는 이 기기에만 암호화되어 저장되며 **백업을 따라 다른 기기로 넘어가지 않습니다**([백업과 이전](#백업과-이전) 참고).

### 사용자가 제어할 수 있는 부분

- **어떤 소스를 켤지** — 원하지 않는 소스는 꺼 두면 선택 회차에서 아예 질의하지 않습니다
- **소스 순서** — 자동 모드의 동점 판정이자 「소스 순서」 모드의 우선순위입니다
- **선택 모드** — 자동(함께 총점 비교) 또는 소스 순서(가사가 있는 첫 소스가 승리)
- **곡별 지정** — 소스 목록에서 후보 하나를 수동으로 고정합니다

## 설치

### 요구 사항

| 항목 | 요구 사항 |
|---|---|
| 시스템 | Android 8.1 이상(minSdk 27, targetSdk 35) |
| 모듈 프레임워크 | **Xposed / LSPosed**(권장, root 필요) 또는 **LSPatch**(root 불필요, Spotify에 직접 패치 필요). 모듈은 Xposed API 102를 사용합니다 |
| Spotify | 이 버전은 **9.1.88 – 9.1.90**에 맞춰 조정되었습니다. 더 이전 버전, 베타 버전, 서드파티 개조판은 동작하지 않을 수 있습니다 |
| 모듈 버전 | 1.4(versionCode 7) |

> 모듈은 Xposed 프레임워크 주입에 의존하므로 **패치하지 않은 Spotify에서는 동작하지 않습니다**.

### 단계

1. [Releases](https://github.com/junxi8686/SpotifyPlusPlus/releases)에서 최신 APK를 내려받아 설치합니다
2. **LSPosed** → **모듈** → **Spotify++**를 활성화합니다
3. **범위**에서 `Spotify`를 체크합니다
   - Android Auto 가사가 필요하면 `Android Auto`도 체크합니다
4. **Spotify를 강제 종료**합니다(설정 → 앱 → Spotify → 강제 종료)
5. Spotify를 다시 엽니다

> ⚠️ **4단계는 건너뛸 수 없습니다.** APK를 설치해도 Spotify 프로세스는 **재시작되지 않으며**, LSPosed는 프로세스가 시작될 때만 모듈을 로드합니다. 이 단계를 건너뛰면 옛 코드를 시험하게 됩니다 — 문제를 찾을 때 가장 흔한 혼란의 원인입니다.
>
> **버전을 업데이트할 때도 마찬가지입니다**: 새 APK를 덮어 설치한 뒤 똑같이 강제 종료하고 Spotify를 다시 엽니다. LSPatch를 쓴다면 「버전 번호 덮어쓰기」를 켜는 것을 잊지 마세요.

## 첫 실행

설치한 뒤 곡을 그냥 재생하면 가사가 자동으로 나타납니다. 첫 곡부터 좋은 결과를 얻도록 모듈은 활성화된 모든 소스에 동시에 질의하고, 이후 소스가 반환되면 다시 비교합니다.

### 설정은 어디에 있는가

두 개의 입구가 있습니다:

- **설정** — Spotify 설정 안의 **Spotify++** 섹션. 모든 스위치가 여기에 있습니다: 가사 소스(활성화, 순서, 선택 모드, 클라이언트 키), 번역(엔진, 대상 언어, 캐시), AI 번역과 독음, 인터페이스와 렌더링, 캐시 지우기, 내보내기와 가져오기
- **소스 목록** — 가사 화면 오른쪽 아래의 소스 버튼. 이 곡에서 각 소스의 매칭 상황을 보고, 하나만 다시 확인하고, 수동으로 지정합니다

### 조정 제안

| 원하는 효과 | 방법 |
|---|---|
| 글자 단위 가사 우선 | 기본으로 켜져 있으며 설정할 필요가 없습니다 |
| 특정 소스 우선 | 설정 → 소스 순서에서 맨 앞으로 옮깁니다. 또는 소스 목록에서 이 곡에 한해 수동 지정합니다 |
| 중국어 곡을 간체로 표시 | 기본으로 켜져 있습니다(간체 정도가 점수에 참여) |
| 가사가 따라오지 않음 / 직접 스크롤 | 「재생 따라가기」를 끕니다 |
| 가사가 어긋남 | 설정 → 가사 동기화 재설정 |
| 소스 하나 덜 질의 | 설정 → 그 소스를 끕니다 |

## 백업과 이전

**설정 → 설정과 데이터 내보내기**는 JSON 파일 하나를 씁니다(기본 `Downloads/Spotify++/SpotifyPlusPlus-backup.json`, 저장 위치를 직접 고를 수도 있습니다). 복원은 **설정과 데이터 가져오기**로 합니다.

### 백업에 포함되는 것

| 내용 | 설명 |
|---|---|
| 모든 설정 | 인터페이스, 렌더링, 동작, 선택 모드 |
| 소스 순서와 곡별 지정 | 직접 조정한 우선순위와 곡별 선택 |
| 전체 카탈로그 | 각 곡에 어떤 소스 후보가 있는지, 매칭 방식, 확인 여부 |
| 가사와 번역 캐시 | 데이터베이스를 통째로 복사하므로 복원 후 다시 내려받거나 번역을 다시 요청할 필요가 없습니다 |
| 가져온 글꼴 | 사용자 글꼴 파일도 함께 가며, 복원할 때 이 기기의 새 경로를 가리킵니다 |
| 자격 증명 암호문 | 클라이언트 키, AI 서비스 키, 번역 인터페이스의 AppID와 키. 이 백업을 만든 설치에서만 풀 수 있으므로 기기를 바꾸면 다시 입력해야 합니다(아래 참조) |
| 약간의 런타임 상태 | 키 버전과 접근 상태로, 복원 후 옛 결과가 섞이지 않게 합니다 |

### 일부러 포함하지 않는 것

- **진단 초안과 캡처 버퍼** — 진행 중인 보고의 임시 상태이며 옮길 대상이 아닙니다
- **언어 모델 패키지** — 수십 MB이고 언제든 다시 내려받을 수 있으며, 설정이 다시 가리킵니다
- **평문 자격 증명** — 암호문만 있습니다. 아래를 참고하세요

### 자격 증명은 따라가지 못한다

자격 증명은 이 기기에 암호화되어 저장되고, 암호화에 쓰는 키는 시스템 Keystore 안에 있으며 이 기기에서의 Spotify 신원에 묶여 있습니다. 그 키는 **백업 파일에 기록되지 않습니다**. 따라서:

- 같은 기기에서는 모듈 업데이트, Spotify 업데이트, 모듈 삭제 후 재설치를 해도 자격 증명을 계속 쓸 수 있습니다
- 휴대폰을 바꾸거나, Android 사용자를 바꾸거나, Spotify 데이터를 지운 뒤에는 백업 안의 암호문을 풀 수 없습니다 — **새 기기에서 다시 입력해야 합니다**
- 모듈은 **키를 가져오거나 이전하지 않으며**, 어떤 안내도 그렇게 말하지 않습니다

복원할 때 이 기기에 이미 쓸 수 있는 자격 증명이 있으면 **파일에서 읽을 수 없는 값으로 덮어쓰지 않습니다.** 복원이 끝나면 어떤 자격 증명을 설정에서 다시 입력해야 하는지 항목별로 알려 줍니다.

### 복원 규칙

- **파일에 있는 항목은 같은 이름의 항목을 덮어쓰고, 파일에 없는 항목은 그대로 둡니다**(옛 버전의 백업도 가져올 수 있으며, 덮어쓰지 않은 부분을 비우지 않습니다)
- 현재 버전보다 새로운 백업은 추측하지 않고 거부합니다
- 복원 후 카탈로그와 번역 캐시는 **Spotify를 재시작해야 적용됩니다**

## 소스에서 빌드

### 환경

| 구성 요소 | 버전 |
|---|---|
| JDK | 17 |
| Android SDK | Platform 35(compileSdk 35 / minSdk 27) |
| Gradle | 8.14.2(wrapper 포함) |
| Android Gradle Plugin | 8.8.2 |
| Xposed API | 102.0.0(`io.github.libxposed:api`) |

### 명령

```bash
git clone https://github.com/junxi8686/SpotifyPlusPlus.git
cd SpotifyPlusPlus
./gradlew :app:assembleDebug          # 산출물은 app/build/outputs/apk/debug/
./gradlew :app:testDebugUnitTest      # 단위 테스트
```

Windows에서는 `gradlew.bat`을 사용합니다.

### 단위 테스트 그룹

테스트는 매번 전체를 돌리지 않고 그룹으로 돌릴 수 있습니다:

```bash
./gradlew :app:testDebugUnitTest -PtestGroup=lyrics        # 가사 관련
./gradlew :app:testDebugUnitTest -PtestGroup=settings      # 설정과 문자열
./gradlew :app:testDebugUnitTest -PtestGroup=corpus        # 언어 골든 샘플
```

사용 가능한 그룹: `settings`, `diagnostics`, `hooks`, `lyrics`, `lyrics-ai`, `lyrics-session`, `corpus`. 그 밖에 명시적으로 켜야 하는 평가 도구(`-PtestTools=jp-export`, `-PtestTools=model-survey`)가 있으며, 이들은 파일을 쓰거나 유료 서비스를 호출하므로 회귀 테스트가 아닙니다.

## 문제 해결

<details>
<summary><b>설치했는데 반응이 없음 / 기능이 동작하지 않음</b></summary>

1. LSPosed에서 모듈이 활성화되고 **범위에 Spotify가 체크**되었는지 확인합니다
2. **Spotify를 강제 종료한 뒤 다시 엽니다** — 필수입니다
3. Spotify 버전이 지원되는지 확인합니다(이 버전은 9.1.88 – 9.1.90에 맞춰 조정되었습니다)

</details>

<details>
<summary><b>가사가 번체인데 간체를 원함</b></summary>

간체 정도가 점수에 참여하므로 간체 문서가 보통 자동으로 이깁니다. 그래도 번체라면:

1. **소스 목록**을 열어 간체 가사를 제공하는 소스가 있는지 봅니다
2. 있으면 그것을 수동으로 지정합니다
3. 없으면 그 곡에 아직 쓸 수 있는 간체 가사가 없다는 뜻입니다 — 채점 규칙이 없는 가사를 만들어 내지는 않습니다

</details>

<details>
<summary><b>어떤 소스가 계속 찾지 못함</b></summary>

**소스 목록**에서 그 줄을 눌러 따로 확인합니다:

- **체크** → 그 소스에 이 곡의 가사가 있습니다
- **빨간 엑스** → 그 소스에 정말 없거나 네트워크가 안 됩니다

가사를 가져오지 못하는 소스는 쓸 수 있는 것처럼 보이지만 눌러도 반응이 없는 상태가 아니라, 사용할 수 없음으로 분명히 표시됩니다. **수록 여부는 동적으로 바뀝니다** — 오늘 없다고 나중에도 없다는 뜻은 아닙니다.

</details>

<details>
<summary><b>키가 필요한 그 소스가 아무것도 내놓지 않음</b></summary>

1. 설정에서 키가 저장에 성공했는지 확인합니다(저장할 때 안내가 나옵니다)
2. 소스 목록에서 **한 번 직접 눌러 봅니다** — 수동 확인은 「명시적 복구」 경로를 타서 이전의 접근 제한을 풀 수 있습니다
3. 서버가 키를 거부한 적이 있으면 그 소스가 일시 중지됩니다

</details>

<details>
<summary><b>휴대폰을 바꾸거나 ROM을 새로 올린 뒤 복원하는 방법</b></summary>

**내보내기와 가져오기**를 사용합니다. 주의:

- 설정, 소스 순서, 카탈로그, 캐시는 모두 복원됩니다
- 자격 증명의 암호문은 파일을 따라가지만 복호화 키는 기기에 묶여 있습니다 — **새 기기에서 다시 입력해야 합니다**
- 복원이 끝나면 모듈이 어느 항목을 다시 입력해야 하는지 구체적으로 알려 줍니다

</details>

<details>
<summary><b>가사가 동기화되지 않음 / 갈수록 어긋남</b></summary>

먼저 소스 목록을 봅니다: 시간축 끝점이 녹음 끝과 멀리 떨어져 있으면 그 문서는 녹음과 같은 버전이 아니므로 다른 것으로 수동 교체할 수 있습니다.

시간축 자체에는 문제가 없다면:

설정 → **가사 동기화 재설정**. 저장된 오프셋을 지우고 모듈이 재생 시계에 다시 맞춥니다.

</details>

## 알려진 문제와 제한

- **점수는 이번 회차의 후보와 관련이 있습니다** — 길이 적합도는 순위로 점수를 주므로 후보가 바뀌면 같은 문서의 총점도 달라질 수 있습니다
- **언어 판정은 휴리스틱입니다** — 가나가 거의 없는 일본어 곡이 중국어로 판정될 수 있고, 영어가 많은 중국어 곡은 한자 밀도 문턱 아래로 떨어질 수 있으며, 한국어 안의 한자는 따로 인식되지 않습니다. 잘못 판정해도 이 항목에서 점수를 덜 줄 뿐 더 주지는 않습니다
- **일부 곡은 느린 소스에서 매칭이 느립니다** — 네트워크 때문이며 모듈 문제가 아닙니다
- **Android Auto 가사**는 일부 차량 헤드유닛에서 충분히 시험되지 않았습니다
- **극소수 곡**은 가사와 녹음 길이가 맞지 않습니다. 10초를 넘는 범위 초과는 제외되지만 10초 이내는 여전히 어긋날 수 있습니다
- **독음은 규칙과 사전으로 구동됩니다** — 보통화 다중음자, 일본어의 예술적 독음, 키릴 문자 전사, 그리스어 정적 표에는 알려진 한계가 있습니다
- **root 없는 LSPatch 방식**은 「다운그레이드—로그인—업그레이드」 절차에 의존하며, 로그인이나 무결성 검사가 실패할 수 있습니다
- **HyperGlow 전송**은 기기가 이 기능을 지원해야 합니다

문제가 있으면 [Issues](https://github.com/junxi8686/SpotifyPlusPlus/issues)에 다음을 포함해 알려 주세요:

- Spotify 버전
- 모듈 버전
- 재현 단계
- 관련 스크린샷

## 이 포크가 바꾼 것

이 저장소는 [Spicy EX](https://github.com/amarinne/spicy-ex) **v2.0.0**을 이 프로젝트의 **v1.1** 위에 병합했고, 1.4에서 그 안의 정렬 규칙을 다시 바꿨습니다:

### 중국어 간체

- `values-zh-rCN`을 추가하고 모든 문자열 리소스를 포함했습니다
- 상류에서 「Java가 참조하지만 리소스에 없는」 문자열 때문에 중국어 인터페이스가 영어로 되돌아가던 문제를 수정했습니다
- 가사 크레딧, 오류 안내 등 동적 문구를 중국어로 옮겼습니다
- 일부 기기에서 언어 목록에 현재 언어만 남고 다시 되돌아오지 못하던 문제를 수정했습니다

### 가사 매칭

- **가중 점수로 최선 선택**(1.4) — 상류 v2.0.0은 「소스 우선」(주 소스를 정하고 그 소스 안에서만 시간축을 비교)으로 바꿔 더 나은 대체 소스가 주 소스를 영영 교체할 수 없게 했습니다. 이 저장소의 v1.1은 품질 우선의 단계별 비교로 되돌렸고, 1.4는 이를 다시 일곱 항목 가중 합산으로 바꿨습니다. [단계별 비교와 가중 점수](#단계별-비교와-가중-점수)를 참고하세요
- **여러 소스 동시 요청** — 상류는 소스를 하나씩 순서대로 요청해 대기 시간이 모든 소스의 합이었습니다. 지금은 동시에 보내고 가장 빠른 것을 먼저 표시하며 점수가 더 높아야 교체합니다
- **이름으로 가사 검색** — 자동 매칭이 실패하면 직접 검색해 고를 수 있습니다
- 간체↔번체 상호 검색과 별칭 변형(「한 글자 차이를 두 곡으로 취급」하던 문제 수정)
- **소스 목록은 곡마다 자동 확인을 한 번만** 하고, 성공할 때마다 알림을 쏟아내지 않습니다
- **다른 버전의 문서 제외** — 녹음보다 10초 이상 긴 후보는 비교에 참여하지 않습니다

### 백업과 기타

- **백업 범위를 2개 저장소에서 설정, 소스 선택, 카탈로그, 캐시, 글꼴, 자격 증명 암호문(이 백업을 만든 설치에서만 복호화 가능)으로 확장** — 상류는 설정과 키만 백업해서 가져온 뒤 카탈로그가 비어 있고 소스도 선택되지 않았습니다
- **자격 증명 보존 규칙** — 복원할 때 이 기기에서 아직 쓸 수 있는 키를 덮어쓰지 않고, 어떤 것을 다시 입력해야 하는지 알려 줍니다
- 더 이상 쓰지 않는 가사 소스 하나를 제거했습니다. 옛 설정이나 옛 백업에 남은 항목도 질의하지 않습니다
- 잘못된 주소를 가리키던 GitHub 링크 세 곳을 수정했습니다
- 설정의 「문제 보고」 항목을 제거했습니다(초안이 상류로 보내져 이 저장소에는 오지 않습니다)
- Spotify 9.1.88 – 9.1.90의 곡 조회와 떠 있는 창을 대응했습니다(상류 방식은 새 버전에서 `NoSuchMethodException`을 던져 자동 검색이 통째로 동작하지 않습니다)
- 번역 경로를 수정했습니다: 중국어 번역이 버려지고, 「번역 중」에 멈추고, 실패해도 안내가 없고, 반복 줄에 번역이 없던 문제

자세한 내용은 [MODIFICATIONS.md](MODIFICATIONS.md)와 [FEATURES_USER.md](FEATURES_USER.md)를 참고하세요.
